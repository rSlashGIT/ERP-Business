===============================================================================
1. EXECUTIVE SUMMARY
===============================================================================

SmartStock is an AI-powered inventory decision-support system for retail
replenishment. It helps a store manager answer one practical question:

    "How much stock should I order today so that I avoid both stockouts and
    overstocking?"

The project combines:

- Real retail demand data inspired by the M5 Walmart dataset.
- Demand forecasting models: Chronos-Bolt, N-HITS, LightGBM, and naive baselines.
- Inventory policy optimization using CMA-ES.
- A context-aware parameterized (s,S) replenishment policy.
- Multi-echelon supply-chain simulation: supplier -> warehouse -> stores.
- Multi-SKU simulation for 30 SKUs.
- Explainability for individual order recommendations.
- Disruption and stress testing.
- Reward-hacking/audit checks to detect policies that look profitable but behave
  unfairly or unsafely.
- A premium interactive frontend demo that can be opened locally with one click.

In simple language:

SmartStock is a prototype of an intelligent retail stock manager. It reads SKU
data, current stock, demand history, forecast signals, supplier delays, and risk
conditions. It then recommends a concrete order quantity such as 300 units,
explains why it chose that quantity, compares models, and lets the user test
what happens under demand spikes or supplier disruptions.

The project is not only a dashboard. The dashboard is the presentation layer.
The technical core is the Python research pipeline that preprocesses data,
evaluates forecasters, simulates supply-chain behavior, optimizes inventory
policies, explains decisions, and produces JSON artifacts for the UI.

2. BUSINESS PROBLEM
===============================================================================

Retail inventory decisions have two opposing risks:

- Under-ordering:
  The store runs out of stock, customers cannot buy the product, sales are lost,
  and service quality drops.

- Over-ordering:
  Too much inventory sits in storage, tying up capital and creating holding cost.

The system is designed for daily replenishment decisions. Every day, for every
SKU, the system must decide whether to order and how much to order.

Core business objective:

    Maximize profit while keeping service level high.

Profit is treated as:

    revenue - holding cost - stockout cost - procurement cost - other penalties

Important business metrics:

- Inventory level.
- Demand forecast.
- Demand uncertainty.
- Supplier lead time.
- Days of cover.
- Recommended order quantity.
- Service level / fill rate.
- Stockout risk.
- Overstock risk.
- Expected coverage after order.
- Policy profit.
- Model forecast error.

11. CORE INVENTORY POLICY
===============================================================================

The project uses a parameterized (s,S) inventory policy.

Classical (s,S) idea:

- s = reorder point.
- S = order-up-to level.
- If inventory falls below s, place an order.
- Order enough to move inventory toward S.
- If inventory is above s, do not order.

SmartStock improvement:

Instead of using fixed s and S, SmartStock makes them context-dependent:

    s(context) = s_base + w1*demand_forecast + w2*demand_std + w3*lead_time
    S(context) = S_base + w4*demand_forecast + w5*demand_std + w6*lead_time

Theta vector:

    theta = [s_base, S_base, w1, w2, w3, w4, w5, w6]

Input state expected by the policy:

- inventory_level
  Normalized current inventory.

- demand_forecast
  Normalized expected demand.

- demand_std
  Normalized demand uncertainty/volatility.

- lead_time
  Days until replenishment arrives.

Decision logic:

    read inventory, forecast, uncertainty, lead time
    compute dynamic s
    compute dynamic S
    if inventory < s:
        qty = max(0, S - inventory)
    else:
        qty = 0
    return nearest valid action index

Action index mapping in the single-SKU environment:

- 0 -> 0 units
- 1 -> 50 units
- 2 -> 150 units
- 3 -> 300 units
- 4 -> 500 units
- 5 -> 750 units
- 6 -> 1000 units
- 7 -> 1500 units

Why this policy is useful:

- It remains understandable to business users.
- It can be tuned with optimization.
- It reacts to demand changes, uncertainty, and lead time.
- It avoids a pure black-box AI decision.

===============================================================================
12. CMA-ES OPTIMIZATION
===============================================================================

CMA-ES means Covariance Matrix Adaptation Evolution Strategy.

In this project, CMA-ES searches for good theta values for the parameterized
(s,S) policy. It does not learn by gradients. It samples populations of
candidate theta vectors, simulates them, ranks them by profit, and updates its
search distribution.

Basic optimization loop:

    initialize theta around default policy
    repeat for generations:
        sample candidate theta vectors
        for each theta:
            build policy
            run inventory simulation episodes
            compute mean profit / fitness
        rank candidates
        update CMA-ES mean, variance, and covariance
        keep best theta
    save best theta and logs

Common hyperparameters documented in the project:

- Population size: 16
- Episodes per generation: 64
- Max iterations: 100
- Early stopping: 35 stagnant generations
- Initial sigma: 5.0
- Main seeds: 42, 123, 456, 789, 999

Why CMA-ES was chosen:

- More stable than the older deep RL attempt.
- Good for small continuous parameter vectors.
- Works with non-differentiable simulations.
- Keeps the final decision rule interpretable.

src/policy_explainer.py

Main functions:

- explain_decision
- make_policy_fn
- generate_sample_explanations

Responsibility:

- Explains order decisions using perturbation-based sensitivity analysis.
- It is policy-agnostic: any callable policy that maps state dict to order
  quantity can be explained.

Explanation approach:

- Take original state and original decision.
- Perturb one feature at a time by -20%, -10%, +10%, +20%.
- Recompute decision.
- Measure sensitivity as decision change divided by perturbation magnitude.
- Rank features by mean absolute sensitivity.
- Generate counterfactual statements.

Feature bounds:

- inventory_level: 0 to 3
- demand_forecast: 0 to 2
- demand_std: 0 to 2
- lead_time: 1 to 10

Output fields:

- original_decision
- original_state
- top_factors
- counterfactuals
- all_sensitivities

17. UI DESIGN OVERVIEW
===============================================================================

The UI is designed as a premium interactive demo rather than a plain admin
dashboard.

Design goals:

- Look polished enough for teacher/customer demonstration.
- Make the project understandable from the UI itself.
- Avoid overwhelming the user with too many separated panels.
- Keep technical depth available through interaction.
- Show the product identity: SmartStock, not a copied external website.

Design style:

- Dark premium base inspired by modern product/storefront interfaces.
- Teal, gold, blue, and warm accent colors.
- Top navigation instead of old left-heavy layout.
- Interactive particles/texture background.
- Dense but readable operational controls.
- Cards and panels grouped by workflow:
  forecast -> decision -> explanation -> risk.

Interactivity:

- Slider changes update recommendation values instantly.
- SKU selection changes charts and context.
- Notification button opens an alert panel.
- Command palette opens with Ctrl/Cmd + K.
- Orders can be approved, modified, or skipped.
- History records actions.
- Stress scenarios can be clicked and compared.

Why this helps the demo:

The evaluator does not need to read code first. They can use the screen and see:

- What product/SKU is being analyzed.
- What the forecast says.
- What the AI recommends.
- Why it recommends it.
- What happens under disruption.
- How decisions are logged.

        -> demo.js updates local state

           nearest valid order action, service/risk signals
        -> _renderDecision updates order cards

    user selects recommendation in Orders

        -> user clicks approve/modify/skip
        -> AppState.recordDecision stores local decision in localStorage
        -> toast confirms action
        -> pending badge/count is updated
        -> History screen can show the decision

    user clicks notification button
        -> header.js toggles notification panel

        -> clicking outside/close hides panel

27. REWARD-HACKING AUDIT
===============================================================================

The project discovered an important issue:

A policy can look profitable while treating one store badly.

Example:

- Uniform CMA-ES had good profit but Store C service level collapsed to about
  61.8% in the frontend comparison.
- The hack detector flags this as store abandonment.

Fix:

- Per-node service-level constraints.
- Robust per-node CMA-ES policy.

Final robust policy:

- Passes reward-hacking checks in hack_detection_report.json.
- Keeps Store C from being abandoned.
- Maintains more balanced service behavior.

Audit checks:

- Store abandonment.
- Constraint migration.
- Generalization gap.
- Degenerate policy.

Why this is important:

It shows the project is not just optimizing a metric blindly. It checks whether
the learned policy is operationally acceptable and fair across stores.

===============================================================================
29. EXPLAINABILITY
===============================================================================

The system explains decisions with sensitivity and counterfactuals.

Example explanation style:

- Lead time was important.
- Demand forecast pushed the order higher.
- Inventory level reduced the need to order.
- If demand were 20% higher, the recommendation would increase.
- If lead time were lower, the recommendation might decrease.

Why this matters:

Teachers, managers, and customers need to trust the recommendation. A number
alone is not enough. The system shows the factors behind the number.

Explainability is not SHAP in this project. It is a simpler perturbation-based
method that is easy to explain:

    change one input
    observe how the decision changes
    rank important inputs

===============================================================================
30. IMPORTANT FORMULAS
===============================================================================

Parameterized reorder point:

    s = s_base + w1*demand_forecast + w2*demand_std + w3*lead_time

Parameterized order-up-to level:

    S = S_base + w4*demand_forecast + w5*demand_std + w6*lead_time

Order decision:

    if inventory < s:
        qty = max(0, S - inventory)
    else:
        qty = 0

Single-SKU environment reward:

    reward = total_revenue - total_cost

Total cost:

    holding_cost + procurement_cost + defect_cost + stockout_penalty

Service level:

    service_level = total_sales / total_demand

Store demand split:

    store_demand = base_demand * store_share * store_multiplier * noise_factor

Multi-SKU warehouse overflow:

    overflow = max(0, total_warehouse_inventory - max_warehouse_capacity)
    overflow_cost = overflow * overflow_penalty

33. LIMITATIONS AND HONEST NOTES
===============================================================================

- The current frontend is a static demo. It uses precomputed JSON files rather
  than calling a live Python backend.

- The Showcase screen recomputes a simplified live decision for interaction.
  The heavy model training and evaluation are precomputed in Python.

- Some PRD numbers refer to earlier single-SKU experiments, while current
  frontend policy numbers reflect later multi-echelon/per-node experiments.

- The app is a prototype, not a production ERP system.

- The project does not currently include authentication, a real database, or
  live supplier/order integrations.

- The UI is designed for demonstration and explanation. Production deployment
  would require backend APIs, access control, monitoring, data refresh jobs,
  and integration with inventory systems.

36. CONCLUSION
===============================================================================

SmartStock is an end-to-end AI inventory optimization prototype. It starts with
retail demand data, evaluates forecasting models, simulates replenishment,
optimizes interpretable ordering policies, explains recommendations, stress
tests disruptions, audits for unsafe behavior, and presents everything through a
premium interactive UI.

The project's biggest strength is that it connects AI modeling to an actual
business action. It does not stop at "demand will be high tomorrow." It says:

    "Order this many units, here is why, here is the risk, and here is how the
    decision behaves under disruption."

That is the complete value of the project.
